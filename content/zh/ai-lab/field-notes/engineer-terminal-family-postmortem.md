> **交付里程碑：2026-10-27。** 该日 Astro TUI 主题与共享主题中心提交完成。这里记录的是 Engineer Terminal 家族第一轮可浏览交付；不同终端子主题仍有各自的日期和能力边界。

## “看起来像终端”不等于终端交互

早期版本主要提供黑底、字符和输入框，用户指出它更像假页面。另一个关键交互约定是：普通输入应被识别为对 Agnes 的自然语言对话，只有 `/` 命令才执行网站操作；回答应在原界面渐进披露，不能随意弹出另一套聊天窗口。这个反馈把设计问题从视觉装饰推进到**输入协议（input contract）**和上下文范围。

## 碰壁：命令、自然语言和页面路由混为一谈

若把所有输入都当命令，用户输入“怎么配置 RAG”只会收到未知命令；若把每段文字都送给模型，`/projects` 等确定性导航又会失去可预测性。若再开一个独立聊天窗口，当前页面、滚动位置和主题上下文会丢失。它们本质上是三个任务：解析确定性命令、理解自然语言、保留跨页面上下文，不应由一个模糊的 `submit()` 分支承担。

## 架构修复

把终端表面拆成命令解析器、对话处理器和路由/数据适配器。命令解析只允许明确的命令语法，未知命令返回本地帮助；普通文本进入 Agnes 流式对话，并留在当前工作台逐步显示；上下文以页面标识、当前主题、用户选择和用户明确提供的内容为来源，按优先级裁剪，并在切页时更新。轻量 RAG 可以检索公开的本地文章索引，但必须保留来源链接、召回边界和无结果回退；它不能假装已经具备任意全站语义理解。

Engineer Terminal 本身提供 `help`、`ls`、`open`、`find` 等本地命令，并把 Hugo 文章与项目数据注入列表。主题中心和主题预览使用明确路由，避免终端入口被主题管理页面占用。命令可执行性、对话安全和目录数据来源应分别测试。

## 前后差异与实践

前一阶段是一个视觉上像终端、但输入语义不清的演示；交付结构把 CLI 变成访问真实内容的入口，并为对话/命令划清职责。2026-10-27 交付记录证明了 Astro TUI 接入与主题中心同步；它不证明 Agnes 全站上下文、RAG 或生产密钥部署已完成。技术栈上，Hugo 管静态内容和路由，独立客户端脚本负责交互；这是静态站可部署性的优势，也意味着需要服务端能力的模型 API 必须走独立后端。

实习生可以用费曼法画出三条数据流：`/open 3 -> 本地解析 -> 站内路由`、`自然语言 -> 服务端模型 -> 增量回答`、`当前页面 -> 上下文构造 -> 可选检索`。每条都写出超时、无权限、无检索结果时的行为。先把边界讲清楚，再谈“智能终端”，才能避免靠动画掩盖交互欠账。
